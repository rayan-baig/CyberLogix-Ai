# Setting up sensors

Step by step, in words, for every way a sensor can report to
CyberLogix. The same guides are in the app at `/help/sensors`.
`https://cyberlogix.example.com` stands for your own address. Every route, header and
field named here is checked against the code by
`tests/test_sensor_guides.py`; this file is generated by
`sensor_guides.py`, so change that rather than this.

## Any device or script that can send a web request

Gateways and hubs that let you set the address, headers and body of what they send; a Raspberry Pi; your own script.

1. In the console, open Setup and use Add a fridge or freezer: say where it is and which industry it is in, so it gets the right limits. Give it a Sensor ID you will recognise, such as WALKIN-1, or leave it blank and one is made from the location. Press Claim a seat.
2. Copy the sensor key the console shows next. It is shown once. It lets a device report readings for this one unit and do nothing else, so it is the key to put on hardware or in a vendor's settings.
3. Set the device to send an HTTPS POST to https://cyberlogix.example.com/api/sensor-pulse every few minutes.
4. Add two headers: X-CyberLogix-Sensor-Key with the sensor key, and Content-Type: application/json.
5. Send a JSON body with sensor_id (the Sensor ID from step 1) and the temperature as temperature_fahrenheit or temperature_celsius. You may add humidity_percent, battery_percent and signal_percent; a battery level lets us warn you before it goes flat.
6. Check the answer. 200 means the reading was taken and the unit shows it in the console. 401 means the key was not recognised; 403 means the key belongs to a different unit; 404 means no unit has that Sensor ID.

What one message looks like:

```json
{
  "sensor_id": "WALKIN-1",
  "temperature_fahrenheit": 2.5,
  "battery_percent": 88
}
```

## Devices that can only put the key in the body (Elitech, Dickson and others)

Wi-Fi and cellular loggers whose cloud forwards each reading to a web address, with a form for the body but no way to add headers.

1. In the console, open Setup and use Add a fridge or freezer: say where it is and which industry it is in, so it gets the right limits, and type the device's own serial number into Third-party device serial. That serial is how a reading finds this unit. Press Claim a seat.
2. Copy the sensor key the console shows next. It is shown once. It lets a device report readings for this one unit and do nothing else, so it is the key to put on hardware or in a vendor's settings.
3. In the device's or vendor's forwarding settings, set the address to https://cyberlogix.example.com/api/v1/bridge/sensor-webhook-ingest and the method to POST, sending JSON.
4. Shape the body with these fields: device_sn (the serial from step 1), api_key_token (the sensor key), reading_value (the number) and metric_type, which says what the number is: temperature_f, temperature_c, humidity_pct, battery_pct, signal_pct. Optionally location_label.
5. Send temperature as its own message from humidity or battery: one reading per message.
6. Check the answer. 200 means it was taken. 202 means the serial is not on any unit yet: the reading is held under Devices knocking in the console, where one tap adds it and keeps what it sent. 401 means the key was not recognised.

What one message looks like:

```json
{
  "device_sn": "ELITECH-00:1B:44:11",
  "api_key_token": "(sensor key)",
  "reading_value": 3.1,
  "metric_type": "temperature_c"
}
```

## Monnit sensors, through iMonnit

Monnit wireless sensors and gateways, with an iMonnit account.

1. In the console, open Setup and use Add a fridge or freezer: say where it is and which industry it is in, so it gets the right limits, and type the device's own serial number into Third-party device serial. That serial is how a reading finds this unit. Press Claim a seat. For Monnit the serial is the sensor's SensorID, the number iMonnit shows for it.
2. Copy the sensor key the console shows next. It is shown once. It lets a device report readings for this one unit and do nothing else, so it is the key to put on hardware or in a vendor's settings.
3. In iMonnit, find where it sends sensor readings on to a web address (a webhook) and give it this address: https://cyberlogix.example.com/api/v1/bridge/any?k=(the sensor key).
4. If iMonnit lets you add a header, send the key in X-CyberLogix-Sensor-Key instead and leave ?k= off the address: an address with a key in it ends up in logs.
5. Nothing needs mapping. We read SensorID as the serial, DataValues as the reading, DataTypes for Celsius or Fahrenheit, MessageDate as when it was taken, and Battery and SignalStrength as battery and signal.
6. One webhook for several sensors: a sensor key only reports for its own unit and refuses the rest with 403. Send the business key in X-CyberLogix-Key instead, and replace it from the console if it is ever seen by somebody it should not be.
7. If nothing appears, open Use a sensor you already own in the console: every payload that reached /api/v1/bridge/any is listed there as it arrived (keys removed), with what was read from it and what was missing. A device that is not listed never reached us.

What one message looks like:

```json
{
  "SensorID": "123456",
  "DataValues": "3.4",
  "DataTypes": "TemperatureC",
  "MessageDate": "2026-11-03 06:00:00",
  "Battery": "92",
  "SignalStrength": "80"
}
```

## SensorPush

SensorPush sensors with a G1 gateway, which reports to SensorPush's own cloud and not to any address you choose.

1. In the console, open Setup and use Add a fridge or freezer: say where it is and which industry it is in, so it gets the right limits, and type the device's own serial number into Third-party device serial. That serial is how a reading finds this unit. Press Claim a seat. For SensorPush the serial is the sensor's id as its cloud names it.
2. The gateway cannot be pointed at us, so the readings have to be fetched from SensorPush's cloud and passed on. Our fetcher (Fetch from a sensor cloud, in the next guide) only sends GET requests with headers you fix in advance. If the account's data can be read that way, use it. If reading it needs a sign-in step that hands out a short-lived token, or a POST, the fetcher cannot do it: run a small relay of your own that reads SensorPush and sends each reading on, as below.
3. The relay sends an HTTPS POST to https://cyberlogix.example.com/api/v1/bridge/any with the sensor key in the X-CyberLogix-Sensor-Key header (or the business key in X-CyberLogix-Key, for several sensors).
4. Each reading as JSON with sensor (the sensor's id), temperature and observed. A SensorPush temperature is read as Fahrenheit, which is what it reports unless the account was changed; if yours is in Celsius, send sensor_id and temp_c instead, which say so.
5. If nothing appears, open Use a sensor you already own in the console: every payload that reached /api/v1/bridge/any is listed there as it arrived (keys removed), with what was read from it and what was missing. A device that is not listed never reached us.

What one message looks like:

```json
{
  "sensor": "16725.1234567890",
  "temperature": 37.4,
  "observed": "2026-11-03T06:00:00Z"
}
```

## Any vendor cloud you can read with a web address

Hardware that only talks to its maker's cloud, when that cloud gives you an HTTPS address that answers with the latest readings as JSON.

1. In the console, open Setup and use Add a fridge or freezer: say where it is and which industry it is in, so it gets the right limits, and type the device's own serial number into Third-party device serial. That serial is how a reading finds this unit. Press Claim a seat. The serial is whatever the vendor's data calls the device.
2. Get the address and the credential from the vendor: an HTTPS address that answers a plain GET with JSON, and the header it wants the credential in, such as Authorization.
3. In the console, open Fetch from a sensor cloud. Give it a name, the address, and the header name and value. Choose how often to fetch: every 5 to 120 minutes, 10 if you leave it.
4. Press Try now. It fetches once and says what came back: readings taken, nothing new, or why nothing could be used.
5. What comes back is read the same way as the send-anything route below: one reading, a list, or readings under samples, readings, data, results or sensors, and each needs a serial that is on one of your units.
6. The address must start with https and point at the public internet. Redirects are not followed: save the final address. After 5 failures in a row it stops asking and the owner is emailed; Try now starts it again.

What one message looks like:

```json
{
  "readings": [
    {
      "device_id": "GW-7781",
      "temp_c": 3.9,
      "timestamp": "2026-11-03T06:00:00Z"
    }
  ]
}
```

## Anything else that sends its own JSON

A device or cloud that sends readings in its own format, with names we have never seen.

1. In the console, open Setup and use Add a fridge or freezer: say where it is and which industry it is in, so it gets the right limits, and type the device's own serial number into Third-party device serial. That serial is how a reading finds this unit. Press Claim a seat.
2. Copy the sensor key the console shows next. It is shown once. It lets a device report readings for this one unit and do nothing else, so it is the key to put on hardware or in a vendor's settings.
3. Point the device at https://cyberlogix.example.com/api/v1/bridge/any with POST and JSON, and the sensor key in the X-CyberLogix-Sensor-Key header. If it cannot set headers, add ?k=(the sensor key) to the address instead.
4. We look for a serial in a field named like one of: device_sn, deviceserial, serialnumber, serial, sensorid, deviceid, device, sensorname, macaddress, mac, imei, id. Case, spaces, dashes and underscores do not matter, and the field may be nested.
5. And for the reading in a field named like one of: reading_value, temperature, temperaturec, temperaturef, tempc, tempf, temp, currentreading, value, reading, datavalue, datavalues, plotvalue, plotvalues, measurement.
6. Celsius or Fahrenheit has to be said, never guessed: in the field name (temp_c, temperatureF), in the value ("3.5 C"), or in the word celsius or fahrenheit. If it is not, the reading is held under Devices knocking and you choose the unit when you add it.
7. Before pointing anything at us, paste one real payload into Use a sensor you already own (it calls /api/v1/bridge/preview). It says what would be read from it and what is missing, and records nothing.
8. If nothing appears, open Use a sensor you already own in the console: every payload that reached /api/v1/bridge/any is listed there as it arrived (keys removed), with what was read from it and what was missing. A device that is not listed never reached us.

What one message looks like:

```json
{
  "Device ID": "DICKSON-7A:2C:19",
  "Temp C": "3.2",
  "Time": "2026-11-03T06:00:00Z"
}
```
